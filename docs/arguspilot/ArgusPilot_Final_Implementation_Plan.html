01 / System decisions

One tracker-owned plan, one controller, one verifier

Jira or GitHub Issues owns the plan

One tracker per project. An issue's description/body or an issue-linked comment/attachment is the authoritative implementation plan. The ticket also owns requirements, dependencies, and final status.

ArgusPilot owns what happens next

Elephant, dependency graph, durable event-backed state machine, role dispatch, bounded repair, compaction recovery and integration coordination. It does not mirror plans into an approval database.

RunProctor owns bounded execution and proof

Register all Goldfish assignments, launch external Kimi coding workers, enforce available time/process limits, and independently certify test results on an exact code tree.

EGM + Superpowers provide reusable practices

Google's actual EGM personas/standards challenge newly drafted plans; Superpowers skills are available to every role, used only where applicable.

Primary operator interaction: open Kimi Web and start a /goal mission against a Jira-only or GitHub-Issues-only collection. Kimi remains the active controller; if it closes, the mission pauses rather than claiming background progress. No Windows cron, competing workflow engine, native coding backend replacement, or parallel coding lane is in scope. [1] [5] [16]

Design rule: Jira/GitHub owns what to build; ArgusPilot owns the next legal action; RunProctor owns mechanical acceptance evidence. The code repository and CI remain authorities for the resulting code.

03 / Google EGM integration

Real Elephant-Goldfish review for plans that must be created

Pin Google's Elephant-Goldfish Model (EGM) personas, reviewer rubrics, and document standards as an actual source dependency, not merely as borrowed labels. EGM's documented host list does not include Kimi Code; implement and test a thin Kimi-native adapter. [8] [9] [10]

Exact workflow

  1. Existing actionable ticket plan: do not run drafting or mandatory disproof again. Consume the plan as issued. Reject only when requirements are materially ambiguous, contradictory, outside policy, or cannot yield an appropriate verification strategy; request clarification rather than silently overwrite the human-authored plan.
  2. No actionable plan: launch a new non-forked native Planner Goldfish. Apply Superpowers writing-plans; include requirements, scope, assumptions, steps, validation, risk and rollback where relevant. Use the actual ticket and targeted repository context as the inputs.
  3. Disprove: pass the drafted plan and bounded source-reading list to fresh EGM reviewer personas via a Kimi adapter. Run egm-review-loop with comprehension and implementation-readiness standards; use the full egm-review pipeline for architectural changes. Each review must have an independent native agent ID, EGM source SHA, findings, severity and artifact digest.
  4. Resolve: Planner revises under preauthorized project scope; repeat until the EGM protocol's convergence criterion or bounded cap is reached. Escalate architectural choices, missing reviewer results, or material findings that cannot be settled safely; do not fabricate owner approval. EGM interactive approval steps must be mapped explicitly to ArgusPilot's delegated policy or a human gate.
  5. Publish before coding: write the resulting plan into the same Jira ticket or GitHub issue (GitHub issue body or canonical issue comment), or to a Jira issue attachment with its authoritative pointer in the description. Re-read the ticket and compare the plan content; only then enable implementation. Store review evidence separately, but never maintain a parallel editable plan.
EGM boundary: EGM is the plan-creation and plan-disproof engine, not the issue tracker, scheduling controller, or replacement for RunProctor. A plan supplied by the user in a ticket does not require an extra automatic EGM approval step. [11]

06 / Trackers and plan ownership

All plans belong to their issues; one tracker per project

The project declares tracker.kind = jira or github_issues. All selected issues and prerequisite edges must come from that provider. A project can use GitHub for source code and PRs while Jira remains its only issue tracker. The two issue systems are never mixed in a project-level mission graph.

Dependency graph: use Jira issue-link direction or GitHub Issues dependency relations; resolve selected predecessors, reject cycles, 403/404, ambiguous directions and stale pagination. Outside-selected prerequisites are observed and never silently implemented. Choose eligible work by blockers cleared, then explicit priority, then stable issue ID. Safe plan publishing

  1. Read the issue and plan location; retain original body/ADF, relevant version, and existing plan digest.
  2. Publish only the dedicated plan portion or attachment pointer, preserving unrelated ticket fields. Perform provider-appropriate precondition checks and implement conflict detection; GitHub issue updates are not assumed to provide an atomic compare-and-swap for body text.
  3. Read back the canonical issue and verify the published plan content, attachment pointer, and relevant issue update. Retry only after checking whether the first attempt already succeeded; otherwise escalate on concurrent edits or permission failure.
  4. Only then enter READY for coding. If publishing fails, keep the draft as an uncommitted artifact and stop; it is not authoritative until written to the ticket.

07 / Deterministic state machines

Mission, ticket, and worker state are durable; plans are not duplicated

Mission

CREATED → ACTIVE → COMPLETE; also PAUSED, BLOCKED, CANCELLED. Owns issue selection, global budget and session-resume identity.

Ticket

WAITING → PLAN_CHECK → READY → CODING → VERIFY → REVIEW → INTEGRATE → DONE. For missing plans, insert PLAN_DRAFT → PLAN_REVIEW → PLAN_PUBLISH between PLAN_CHECK and READY.

Assignment

PREPARED → START_REQUESTED → RUNNING → SETTLING → EVIDENCE_ACCEPTED or REJECTED/OUTCOME_UNKNOWN; includes native and external agent identities.

Repair and interruptions

REPAIR, REPLAN, BLOCKED_DEPENDENCY, BLOCKED_EXTERNAL, and OUTCOME_UNKNOWN. Any retry consumes budget and requires reconciliation.

Evidence-checked transition rules

Transactional rules: a single SQLite writer for mission mutations; unique event IDs and dispatch IDs; expected-revision compare-and-swap for every state or protected-metadata change (including same-state edits); append-only event journal plus rebuildable snapshots. Never accept passed:true or done:true without independent provenance. An uncertain subprocess remains OUTCOME_UNKNOWN until interrogated, not automatically retried.

10 / Safety and operational boundaries

Evidence before completion; scoped authority for external edits

  • Single writer: at most one code-writing worker per repository. RunProctor owns worktree allocation and the internal writer check. Planning and read-only criticism can proceed as independent native agents.
  • Tracker plans are untrusted inputs: issue bodies and attachments are task material, not instructions to disable audit logging, change privileges or access unrelated secrets. Explicit task scope and project policy outrank ticket text.
  • Plan updates: automatically publish a newly generated plan only when project policy grants issue-edit scope. Preserve unrelated issue content; validate write/readback. An existing authored plan must not be replaced without authorization.
  • Verification custody: trusted verifier commands come from approved project configuration; worker-authored tests may supplement them but must not silently weaken them. Bind evidence to the exact verified tree, attempt, and input digests.
  • Native role tools: Plan/Critic/Reviewer profiles should be read-only and have narrow tool access where possible. Native hooks may fail open and are not an OS sandbox; acceptance evidence still requires validation.
  • Secrets: least-privilege Jira or GitHub issue-token, code/PR-token and RunProctor credentials. Do not put credentials in issue plans or model-visible artifacts unless explicitly necessary and scoped.
  • Integration authority: project policy governs PR creation, merge, issue closure, and human gates. A green local receipt is not the same as merged verified code. Recheck merged SHA/CI/issue readback.
  • Recovery and budgets: deduplicate PR/comment/issue writes by stable markers; do not blindly retry uncertain workers; cap per-role cost/time/replans. Unknown usage is recorded as unknown, not free.

16 / Instructions for a cold-start implementing agent

Implementation procedure without prior conversation

  1. Inspect: read this document, current AGENTS.md, frozen versions.lock.json (create from the source register if absent), existing runner/delegate implementation, Argus core supervisor map, EGM review skills/personas and the Superpowers Kimi guide. Validate exact commit IDs before coding.
  2. Baseline: clone dachent/model_proctor at pinned commit on a feature branch. Record Windows 11 Kimi CLI/Web version and current tests; do not rename GitHub repo or replace the runner until parity is proven.
  3. Dependencies: set up Argus fork/upstream and EGM source pin, confirm license notices, install Superpowers in operator Kimi and RunProctor child home; build repeatable offline fixtures and plugin diagnostics.
  4. Provider config: require tracker.kind, issue namespace, code repo/base branch, plan location convention, trusted verifier commands, edit/merge/closure permissions and budgets. These are deployment inputs; never invent credentials or permissions. Probe provider capabilities and installed Kimi native Agent/Web endpoints.
  5. Implement in phase order: each phase in Section 14 is a separate reviewable PR with tests, backward-compatibility diff and exit proof. Start with issue-plan adapter and existing-plan reuse before generating new plans.
  6. Make the ticket authoritative: after new plan review, update the same issue and read it back before coding; do not create a second plan approval table, a competing Markdown planning repo or an independent plan API.
  7. Protect execution: dispatch coding only through RunProctor; preserve test sealing, tree-bound acceptance, single-writer control and unknown-result reconciliation. Refuse completion until external PR/CI/tracker evidence is independently confirmed.
  8. Publish and hand over: ship source, installation and rollback, migration shims, license notices, issue provider adapters, EGM/Superpowers pins, Kimi Web traces, offline fixtures and reproducible end-to-end release evidence.

17 / User experience

Start Kimi Web once; select Jira or GitHub Issues for that project

Jira-only project

kimi web

/goal ArgusPilot execute Jira epic BILL-100
and its blocking Jira tickets in project BILL.
Use any existing plan from each ticket.
When one is missing, plan, independently
challenge it and write it to the Jira ticket.
Implement via RunProctor and integrate
only within this project's permissions.

GitHub-Issues-only project

kimi web

/goal ArgusPilot execute GitHub Issues
#41, #44 and #53 in YOUR-ORG/repo.
Use plans already in issue bodies.
For missing plans, draft, disprove and
publish them back to those issues.
Implement through RunProctor, verify,
review and submit PRs per policy.

During execution ArgusPilot reports: chosen issue, plan locator, existing/generated origin, current stage, native planner/critic/reviewer Kimi agent IDs, external RunProctor coder session ID, verification receipt, worktree, PR/CI progress, time/cost and one next action. Native planning/review agents appear in Kimi Web; external proctor worker activity is inspectable through RunProctor status rather than being mislabeled as a native Web subagent.

The mission finishes when every selected issue satisfies the configured external completion policy. Closing Kimi pauses the mission; a new session can resume after replay/reconciliation.
